# 会话版多智能体协作：调研、问题与设计

本文说明会话版（Social mode）群聊为什么要从「每人自己判断要不要说话」改成「先编排、再分工、再复核汇总」，以及新流程的具体规则。代码在 `ui/src/social/collab.ts`（编排器，纯逻辑）和 `ui/src/social/socialSendGroupLoop.ts`（接入会话版 UI）。

## 1. 旧流程的问题

旧的群聊循环（`groupLoop.ts` + `socialSendGroupLoop.ts` 旧版）大致是：每条新消息出现后，**每个成员各自调用一次模型判断「要不要回复」**，选出一个人说话，然后再对他的回复重复这个过程，直到没有人愿意说话。

实际使用中暴露的问题：

| 现象 | 原因 |
| --- | --- |
| 经常没人回答 | N 个成员各自做 reply/silent 判断，模型偏保守时全部选 silent；判断失败（超时、格式不对）也按 silent 处理 |
| 回答前要等很久 | 每轮都要先跑 N 次判断，才开始真正的回答 |
| 多人不如一人 | 成员之间没有分工，各自从头回答同一个问题；后发言的人看不到「自己该做哪一部分」 |
| 提示词偶尔失效 | `runOne` 创建时按值捕获了 `freeReply`、`turnPaused` 等变量，循环里改了值也传不进去（已修复，见 `socialSend.ts` 的 `turnState`） |
| 状态行卡在「正在判断…」 | 状态文案是创建时的快照，后续不再更新 |
| 回答里的换行、列表被压平 | `visibleReplyAfterJudge` 把所有空白合并成一个空格 |
| 出错时一片沉默 | 模型报错只弹一个 toast，群里没有任何说明 |

## 2. 调研：别人是怎么做的

- **Anthropic「Building effective agents」/ multi-agent research system**：效果好的多智能体系统几乎都是 *orchestrator–worker*：一个编排者先理解任务、拆分、指派，worker 拿到**明确的目标、交付格式和边界**后各做各的，最后由编排者汇总。他们特别强调「按任务难度决定投入多少个 agent」——简单问题一个人答，复杂问题才并行。
- **Microsoft Magentic-One**：编排者维护 *task ledger*（目标、已知事实、计划）和 *progress ledger*（谁在做什么、是否卡住），卡住时重新规划或换人。
- **AutoGen SelectorGroupChat / Swarm**：由一次模型调用（或规则）选下一位发言人，而不是让每个人自己举手；成员可以通过显式 handoff 把话题交给指定同事。
- **Mixture-of-Agents / 多视角讨论**：多个模型（角色）独立给出答案，再由聚合者综合，质量通常优于任何单个答案——前提是聚合者看得到所有答案、并被要求取长补短而不是简单拼接。
- **生成者–评审者（generator–critic）循环**：一个成员产出，另一个职责合适的成员审查，给出 APPROVE / CHANGES，产出者按意见修改一次。代码类任务收益最明显。
- **CrewAI / MetaGPT（SOP）**：按标准作业流程定义角色的先后顺序（产品 → 架构 → 开发 → 测试），每一步的产出作为下一步的输入。

共同结论：**1+1>2 来自分工和信息流，而不是让更多人对同一问题各说一遍。**

## 3. 新流程

每条用户消息：

1. **编排（一次模型调用）**：用你在「设置 → 模型」里配置的主模型，以 classify 模式（单条 JSON、无工具）生成计划。不需要额外的「轻量模型」。
2. **按模式执行**：
   - `chat` 寒暄：1–3 人各回一句（@全体 时所有人）。
   - `answer` 单人负责：最常见。只让最合适的一位完整做完。
   - `parallel` 并行分工：2–4 人同时做互不重叠的子任务（并发上限 2），最后由 lead 汇总。
   - `pipeline` 接力流水线：按依赖顺序执行，后一步能看到前一步的交付，做完自己那步就停。
   - `discuss` 多视角讨论：依次发言，后发言者只补充新观点（没有可补充时输出 PASS），最后汇总共识和分歧。
3. **复核**：涉及改代码、对外发送、重要结论时，安排一位职责合适且不是执行者的成员复核。第一行 `APPROVE` 或 `CHANGES`；`CHANGES` 时原执行者按意见修订**一次**。
4. **汇总**：有两位以上成员贡献时，由 lead 把成果整合成一条给用户的最终答复。
5. **成员间交接**：成员在回复里写「@名字 + 具体请求」时，被 @ 的同事会接着回应（每轮最多 3 次，每人最多 1 次），不会无限互相 @。

### 可靠性兜底

- 计划 JSON 解析失败会带着错误提示重试一次；仍失败或模型报错，就退回「最合适的一位成员直接回答」（按职责关键词打分），**保证至少有一个人回答**。
- 被分配的成员回复为空时自动重试一次（提示「这次必须直接给出回复」）；报错时把任务转交给下一位合适的成员，并在群里说明。
- 所有成员都失败时，群里会显示一条带错误原因的提示，引导检查「设置 → 模型」。
- 用户 @ 了某人只安排被点名的人；@全体 时所有人参与。
- 单轮发言上限 `min(14, max(6, 成员数 × 3))`；成员向用户提问时整轮暂停，等用户回复。

### 界面

- 群里会出现一张「协作计划卡」：模式、目标、每一步由谁做什么、交付物、复核人和汇总人。纯问答和寒暄不显示，避免刷屏。
- 状态行实时显示「正在安排分工… / 某某 正在复核… / A、B 正在同时处理…」。
- 回答保留原有的换行、列表和代码块。

### 与插件的联动

编排者的提示词里会列出已启用且已配置凭据的插件（例如「GitHub：搜索 Issue / PR、读取 PR 改动；创建 Issue（需用户确认）」），需要这些数据或操作的步骤会被标成 `tools: true`，执行该步骤的成员就能调用插件工具。见 [plugins.md](./plugins.md)。
